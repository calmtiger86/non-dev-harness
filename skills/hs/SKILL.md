# hs — 하네스 세팅

프로젝트 폴더에 세션 기록용 파일 5개와 git 작업 기록을 세팅합니다. /hs는 프로젝트 폴더 전용이며, 홈 폴더나 `~/.claude` 같은 넓은 폴더에는 세팅하지 않습니다.

## 절대 규칙

- 미리보기 본문은 질문 도구를 부르기 **전에** 일반 글로 출력합니다. 질문 문장에도 핵심(만들·고칠 파일, 커밋 메시지)을 넣습니다. 미리보기를 실제로 출력하지 않았으면 "위 미리보기"라고 쓰지 않습니다.
- 미리보기를 보여 주고 사용자가 확인하기 전에는 아무것도 쓰지 않습니다. git init, `.gitignore`, 기록 파일, git 설정, 커밋이 모두 여기에 들어갑니다.
- 이미 있는 기록 파일(JOURNAL.md, MEMORY.md, ERROR.md, ISSUE.md, WIKI.md)은 어떤 모드에서도 다시 만들거나 덮어쓰지 않습니다.
- 기존 CLAUDE.md는 템플릿 구조에 맞추지 않습니다. 섹션의 순서·제목·내용은 아래 '2. 모드별 할 일'에서 정한 곳 말고는 그대로 두고, 100줄을 넘어도 기존 내용을 줄이지 않습니다.
- git 사용자 정보는 `git config --local`로만 설정하고 `--global`은 쓰지 않으며, 이름·이메일을 지어 넣지 않습니다. GitHub 저장소는 `--private`로만 만들며, 공개는 사용자가 따로 요청할 때만 합니다.

## 도구 쓰는 법

- 사용자가 고르는 질문은 모두 선택지 질문 도구(AskUserQuestion)로 묻습니다. 도구가 없을 때만 번호 목록 글로 묻습니다. 한 번에 한 주제씩 묻습니다.
- 파일 읽기는 Read·Glob·Grep 도구로만 합니다. 하네스 표식 찾기, 템플릿 읽기, 기록 파일 읽기에 Bash `head`·`cat`·`for`·`while`·변수를 쓰지 않습니다.
- 검사 스크립트는 본문의 한 줄을 단독으로 실행합니다. 앞뒤에 `cd`·`&&`·`;`·파이프·변수를 붙이지 않습니다.
- git 명령의 경로는 변수에 담지 않고 하나씩 따옴표로 감싸 적습니다(zsh는 변수 안의 공백으로 경로를 나누지 않아 명령이 실패합니다).
- 사용자에게 보이는 문장은 진행 안내까지 모두 한국어로 씁니다.

## 언제 사용

- 새 프로젝트를 시작할 때 (최초 1회)
- 기존 프로젝트에 하네스를 추가할 때
- 하네스 설정을 다시 하거나 업데이트할 때

## 프로세스

### 1. 상태 판별 (읽기만)

WHY: 엉뚱한 폴더에 세팅하거나 쌓인 기록을 덮어쓰면 되돌리기 어렵다.

이 단계에서는 아무것도 쓰지 않습니다. 아래를 위에서부터 확인해 처음 맞는 모드를 정합니다. 판별한 모드와 그 모드에서 할 일을 한두 문장으로 알리고 진행할지 묻습니다(진행 / 멈춤).

**위험 폴더 목록.** (가) 홈 폴더 자체, 드라이브 루트(`/`, `C:\`, Git Bash에서는 `/c`), `/Users`·`/home`·`C:\Users` 자체(Git Bash에서는 `/c/Users`), `~/.claude`와 그 하위. (나) 홈 바로 아래의 Desktop·Documents·Downloads·바탕화면·문서·다운로드 폴더 자체, OneDrive 폴더 자체(`~/OneDrive`, `~/OneDrive - <회사 이름>`)와 그 바로 아래의 Desktop·Documents·바탕 화면·문서 폴더.

**1) 하네스 찾기.** 현재 폴더부터 한 단계씩 위로 올라가며 각 폴더의 CLAUDE.md 첫 줄을 Read나 Grep 도구로 파일에서 직접 읽습니다. 첫 줄이 `<!-- non-dev-harness:`로 시작하는 CLAUDE.md를 처음 만난 폴더가 하네스 루트입니다. 홈 폴더에 닿으면 멈추고, 홈 폴더 자체는 검사하지 않습니다. 대화에 자동으로 실린 CLAUDE.md에는 HTML 주석이 지워져 있으므로 그것으로 판단하지 않습니다.

- 상위 폴더에서 찾았으면 "상위 폴더 <경로>에 하네스가 있습니다"라고 알리고 그 폴더 기준으로 진행할지 묻습니다. 아니라고 하면 멈춥니다. 하위 폴더에 두 번째 하네스를 만들지 않습니다.
- 하네스 루트가 위험 폴더 목록 (가)에 들면 진행하지 않고 멈춥니다.
- 하네스 루트가 (나)에 들면, 개인 파일까지 함께 기록될 수 있다고 설명합니다. 옮기는 방법(새 프로젝트 폴더를 만들고, 하네스 파일과 이 프로젝트의 작업 파일을 그 안으로 옮긴 뒤, 그 폴더에서 /hs를 다시 실행)을 안내하고, 사용자가 그래도 여기서 진행하겠다고 분명히 고를 때만 진행합니다.
- 표식이 `<!-- non-dev-harness:v1 -->`이거나, JOURNAL.md 없이 하네스 형식 MEMORY.md(첫 줄이 `— 메모리`로 끝남)만 있으면 **업그레이드 모드**입니다.
- 그 밖에 표식이 `<!-- non-dev-harness:v2 -->`이면 **업데이트 모드**입니다.

**2) 하네스가 없을 때**

- **위험 폴더**: 현재 폴더가 위험 폴더 목록 (가)나 (나)에 들면 멈추고, "이 폴더는 범위가 넓어 개인 파일까지 기록될 수 있습니다. 프로젝트용 새 폴더를 만들고 그 안에서 /hs를 다시 실행해 주세요"라고 안내합니다.
- **상위 git 저장소**: `git rev-parse --show-prefix`가 성공하고 출력이 비어 있지 않으면 현재 폴더는 더 큰 저장소의 하위 폴더입니다. `git rev-parse --show-toplevel`로 얻은 경로를 넣어 "이 폴더는 <경로>에 있는 더 큰 git 저장소의 일부입니다. 여기에 세팅하면 기록은 그 저장소 안에 남고, /co는 이 폴더 안의 변경만 저장합니다"라고 알리고 계속할지 묻습니다. 계속하면 git init은 하지 않습니다.
- **파일이 너무 많음**: `find . -maxdepth 4 -type f -not -path './.git/*' | head -n 2001 | wc -l`로 현재 폴더와 그 아래 3단계 하위 폴더까지의 파일 수를 셉니다. 2,000개를 넘으면 "파일이 2,000개가 넘습니다. 프로젝트 폴더가 맞는지 확인해 주세요"라고 경고하고 계속할지 묻습니다.
- 현재 폴더에 CLAUDE.md가 있으면 **덧붙이기 모드**, 없으면 **새로 만들기 모드**입니다.

**3) 기록 파일 하나씩 확인.** 모드와 관계없이 JOURNAL.md, MEMORY.md, ERROR.md, ISSUE.md, WIKI.md를 각각 확인합니다. 이미 있는 파일은 만들지 않습니다. 첫 줄이 하네스 제목 형식(`# <이름> — 작업 일지`, `— 메모리`, `— 에러 이력`, `— 이슈`, `— 위키`)이 아닌 같은 이름 파일은 그대로 두고, 그런 파일이 있다는 사실을 사용자에게 알립니다.

### 2. 모드별 할 일

WHY: 다시 실행할 때 필요한 부분만 고쳐야 쌓인 기록이 사라지지 않는다.

- **새로 만들기**: 템플릿으로 기록 파일 5개(CLAUDE.md, JOURNAL.md, ERROR.md, ISSUE.md, WIKI.md)를 만듭니다(이미 있는 파일은 빼고). 현재 폴더에 `AGENTS.md`가 있으면 새 CLAUDE.md의 설명 줄 아래에 `@AGENTS.md` 한 줄을 넣습니다.
- **덧붙이기**: 기존 CLAUDE.md 내용은 한 글자도 바꾸지 않습니다. 맨 앞에 표식 한 줄을 새로 넣고, 파일 끝에 템플릿의 `## 하네스 파일 안내`부터 `## 변경이력`까지를 덧붙입니다. 기존 CLAUDE.md에 같은 제목(`## 원칙`, `## 프로젝트 규칙`, `## 변경이력` 등)이 이미 있으면 그 섹션은 덧붙이지 않고 알립니다. 100줄 기준은 덧붙인 부분에만 적용하며, 기존 내용을 줄이거나 요약하지 않습니다. 다른 기록 파일은 없는 것만 만듭니다.
- **업데이트**: CLAUDE.md는 `## 프로젝트 정보` 섹션만 Edit로 고칩니다. 그 섹션이 없으면 새로 만들지 묻고, 만든다면 첫 `##` 섹션 바로 위에 넣습니다. 빠진 기록 파일만 템플릿으로 만들고, `.gitignore`에 빠진 줄이 있으면 추가를 제안합니다. 다른 섹션과 기존 기록 내용은 건드리지 않습니다.
- **업그레이드(v1에서 v2로)**: 실제 v1 프로젝트의 CLAUDE.md는 템플릿과 구성이 많이 다릅니다. 템플릿 구조를 강요하지 않고, 기존 기록 내용은 제목 줄을 빼고 한 줄도 바꾸지 않으며, 아래만 합니다.
  - 하네스 형식 MEMORY.md(첫 줄이 `— 메모리`로 끝남)의 이름을 JOURNAL.md로 바꿉니다. 첫 줄이 그 형식이 아니면 사용자가 직접 만든 파일일 수 있으므로 바꾸지 않고 알립니다. JOURNAL.md가 이미 있으면 이름을 바꾸지 않고 알립니다. 하네스 루트에서 `git ls-files --error-unmatch "MEMORY.md"`가 성공하면(git이 추적하던 파일) `git -C "<하네스 루트>" mv "MEMORY.md" "JOURNAL.md"`, 실패하거나 git 저장소가 아니면 `mv`를 씁니다. 일지가 상한(세션 로그 5개 등)을 넘었어도 이름만 바꾸고, 정리는 다음 /co 때 묻도록 둡니다.
  - 일지 제목 줄(첫 줄)이 `— 메모리`로 끝나면 그 부분만 `— 작업 일지`로 바꿉니다.
  - CLAUDE.md 첫 줄 표식을 `<!-- non-dev-harness:v2 -->`로 바꿉니다.
  - `## 하네스 파일 안내` 표가 있으면 Edit 한 번으로 `| MEMORY.md |`라는 글자만 `| JOURNAL.md |`로 바꿉니다. 그 행의 설명 칸은 바꾸지 않습니다. 그 밖에 사용자가 쓴 `MEMORY.md` 언급(변경이력 행 등)은 목록으로 보여 주고 바꿀지 묻습니다.
  - 없는 v2 섹션(`## 기록 파일 다루는 법`, `## 원칙`)만 템플릿에서 가져와 덧붙입니다. `## 프로젝트 규칙`이 있으면 그 바로 위에, 없으면 `## 변경이력` 바로 위에, 둘 다 없으면 파일 끝에 넣습니다. 기존 섹션은 옮기지 않습니다.
  - `## 변경이력` 표가 있으면 오늘 날짜로 v2 업데이트 행을 하나 추가하고, 없으면 건너뜁니다.
  - 빠진 기록 파일(ERROR.md, ISSUE.md, WIKI.md 등)은 템플릿으로 만듭니다. 이미 있는 파일은 건드리지 않습니다.
  - `.gitignore`에 v1 줄이 남아 있으면 따로 묻습니다. `*.key` 줄은 Keynote 발표 파일까지 백업에서 빠지게 하므로 지울지 묻고, `.env*` 줄은 `.env.example`까지 빼므로 `.env`, `.env.*`, `!.env.example` 세 줄로 바꿀지 묻습니다.
  - `## 토큰 절약 규칙` 섹션이 있으면 아래 v1 원문과 똑같은 줄만 지우자고 제안합니다. 사용자가 고치거나 더한 줄은 남기고, 남은 줄이 없을 때만 섹션 제목도 지웁니다. 섹션이 없으면 건너뜁니다.

```
1. 큰 파일은 offset/limit으로 필요한 부분만 읽기
2. 같은 파일 중복 읽기 금지
3. git diff는 --stat 우선, 전체 diff는 필요 시만
4. 로그는 최근 3-5개만
5. 응답은 핵심만 간결하게
6. 컨텍스트 65% 도달 시 /compact 안내 (힌트 포함)
```

### 3. 인터뷰

WHY: 프로젝트 맥락을 알아야 적절한 규칙을 만들 수 있다.

- 새로 만들기: 아래 5문항을 가설-확인 방식으로 한 번에 하나씩 묻습니다. 폴더 이름, 파일, 앞 답에서 추론한 값을 첫 선택지로 두고, 직접 입력은 도구가 붙여 주는 기타(Other)로 받습니다. 후보가 하나뿐이면 둘째 선택지는 "다른 이름으로 할게요"처럼 직접 입력을 안내하는 항목으로 둡니다. 2번은 건너뛰지 않습니다. 앞 답에서 추론할 수 있어도 추론값을 첫 선택지로 두고 확인받습니다.
- 덧붙이기: 기록 파일 제목에 쓸 프로젝트 이름만 확인합니다.
- 업데이트: 지금 `## 프로젝트 정보`의 값을 보여 주고 바꿀 항목만 묻습니다. 섹션이 없고 새로 만들기로 했으면 2~5번을 묻습니다.
- 업그레이드: 인터뷰하지 않습니다.
- 업데이트·업그레이드에서 빠진 기록 파일을 만들 때 `{{PROJECT_NAME}}`은 CLAUDE.md의 첫 `#` 제목에서 가져옵니다.

1. **프로젝트 이름**: 폴더명에서 추론하여 제안 → 확인/수정
2. **무엇을 하는 프로젝트인가요?**: 1-2문장 (예: "블로그를 운영합니다")
3. **누구를 위한 건가요?**: 대상 (예: "개인 사용", "고객용")
4. **사용 도구**: "어떤 도구나 프로그램을 쓰시나요?" — "없음/모름"도 유효한 답변
5. **선호 언어**: 기본값 한국어

5개 항목이 채워지면 인터뷰를 끝냅니다.

### 4. git 준비 (묻기만 하고 실행하지 않음)

WHY: 비개발자가 git을 잊어도 작업이 안전하게 기록되어야 한다. 실행은 미리보기 확인 뒤에 한다.

- git 저장소가 아니면(`git rev-parse --is-inside-work-tree` 실패) "작업 기록(git)을 켤까요?"라고 묻습니다(켜기(추천) / 켜지 않기). 거절하면 git과 `.gitignore`, GitHub 단계를 모두 건너뜁니다.
- `.gitignore`가 없으면 아래 블록으로 새로 만들고, 있으면 블록에서 빠진 줄만 파일 끝에 블록 순서대로 덧붙입니다. 기존 줄은 지우거나 순서를 바꾸지 않습니다(업그레이드 모드의 v1 줄 질문은 예외).
- `git config --get user.name`이나 `git config --get user.email`이 비어 있으면 기록에 남길 이름과 이메일을 사용자에게 묻습니다.

```
# non-dev-harness
```

### 5. 품질 검증 → 미리보기 → 확인

WHY: 사용자가 쓰일 내용과 실행될 동작을 먼저 봐야 원치 않는 변경이 생기지 않는다.

새로 만들기와 덧붙이기 모드에서는 CLAUDE.md를 아래 기준으로 약식 검증합니다.
- [ ] 명령어 안내 있음 (/ci, /co)
- [ ] 파일 구조 테이블 있음
- [ ] `## 기록 파일 다루는 법` 있음
- [ ] `## 원칙` 있음
- [ ] 100줄 이하 (덧붙이기 모드는 덧붙인 부분만)
- [ ] 프로젝트 고유 정보 포함
- [ ] 바로 실행 가능 (ci/co 가능)

미리보기 본문을 먼저 일반 글로 출력합니다. 담을 것은 다음과 같습니다.
- 만들 파일: 파일마다 이름과 내용(CLAUDE.md는 전문, 나머지는 첫 줄과 섹션 제목)
- 고칠 파일: 바뀌는 줄의 전과 후
- 실행할 동작: git init 여부, `.gitignore`에 넣을 줄, `git config --local`로 넣을 이름과 이메일, 이름 바꾸기, 커밋할 파일 목록, 커밋 메시지

그다음 질문 도구로 저장 / 고칠 부분 있음 / 취소 가운데 고르게 합니다. 질문 문장에 핵심을 넣습니다(예: "CLAUDE.md 등 파일 6개를 만들고 git을 켠 뒤 'hs: 하네스 세팅'으로 커밋할까요?"). "저장"일 때만 6단계로 갑니다. 고칠 부분이 있으면 반영해 다시 보여 주고, 취소하면 아무것도 쓰지 않고 멈춥니다.

### 6. 실행

확인받은 것만 이 순서로 실행합니다. git 명령은 `git -C "<하네스 루트>"`로 실행해, 현재 폴더가 하네스 루트가 아니어도(상위 폴더 하네스) 경로가 어긋나지 않게 합니다.

6-1. git init (사용자가 동의했고 저장소가 없을 때만): `git init "<하네스 루트>"`
6-2. `.gitignore` 만들기, 또는 빠진 줄 덧붙이기
6-3. 기록 파일 만들기와 고치기 (아래 템플릿과 치환 규칙)
6-4. 이름과 이메일을 물었다면 `git -C "<하네스 루트>" config --local user.name "<이름>"`, `git -C "<하네스 루트>" config --local user.email "<이메일>"` (저장소가 있어야 하므로 git init 뒤에 합니다)
6-5. 스테이징: 이번에 만들거나 고친 하네스 파일과 `.gitignore`만 경로를 하나씩 적습니다. `git add -A`나 `git add .`는 쓰지 않습니다. 업그레이드에서 이름을 바꾼 MEMORY.md는 넣지 않습니다(`git mv`가 이미 스테이징했습니다).
   `git -C "<하네스 루트>" add -- "CLAUDE.md" "JOURNAL.md" "ERROR.md" "ISSUE.md" "WIKI.md" ".gitignore"` (실제로 만들거나 고친 파일만)
6-6. 검사: 아래 한 줄만 단독으로 실행합니다. 덧붙이기의 기존 CLAUDE.md처럼 사용자가 쓴 내용이 처음 기록될 수 있기 때문입니다.

```bash
bash "${CLAUDE_SKILL_DIR}/../co/scripts/check-staged.sh" "<하네스 루트>"
```

   - `[이름]`, `[내용]`, `[크기]` 머리말 아래에 걸린 파일이 `:(top)경로` 모양으로 나옵니다. 마지막 줄 `[끝]`이 없거나 종료 코드가 0이 아니면 검사 실패이므로 6-5에서 스테이징한 파일을 `git -C "<하네스 루트>" reset -q -- "CLAUDE.md" …`로 되돌리고 멈춥니다. 기록 파일은 그대로 두고, /co를 하면 다시 검사해 기록한다고 안내합니다.
   - 걸린 파일이 6-5에서 스테이징한 파일이면 같은 방법으로 되돌리고 멈춘 뒤, 어떤 파일이 왜 걸렸는지 쉬운 말로 설명합니다. 비밀 값 자체는 출력하지 않습니다. 사용자가 비밀이 아니라고 분명히 말하면 다시 스테이징하고 검사에 `--allow "<걸린 경로>"`를 붙여 그 파일을 뺍니다.
   - 걸린 파일이 사용자가 미리 스테이징해 둔 다른 파일이면 그 사실만 알리고 진행합니다. 6-7 커밋은 경로를 지정하므로 그 파일은 들어가지 않습니다.
6-7. 커밋: 6-5와 같은 경로를 지정해, 사용자가 미리 스테이징해 둔 다른 파일이 섞이지 않게 합니다. 업그레이드에서 MEMORY.md가 git이 추적하던 파일이었으면(`git mv`를 썼으면) "MEMORY.md"도 커밋 경로에 넣어 이름 바꾸기가 기록되게 합니다.
   `git -C "<하네스 루트>" commit -m "hs: 하네스 세팅" -- "CLAUDE.md" "JOURNAL.md" …`

커밋 메시지는 새로 만들기·덧붙이기 모드에서 `hs: 하네스 세팅`, 업데이트·업그레이드 모드에서 `hs: 하네스 v2 업데이트`입니다.

Cowork에서 커밋할 때 "이 폴더 안의 파일을 영구 삭제하도록 허용할까요?" 같은 확인 창이 뜨면, git이 이 프로젝트 폴더 안(`.git` 폴더)에 잠깐 만든 잠금 파일을 지우려는 것이고 작업 파일을 지우는 것이 아니라고 쉬운 말로 설명합니다. 사용자가 허용하지 않으면 커밋을 건너뛰고, 만든 기록 파일은 그대로 둔 채 "git 기록은 내 컴퓨터의 터미널이나 Claude Code에서 /co를 하면 함께 남습니다"라고 안내합니다. 이때 7단계 GitHub 연결도 건너뜁니다.

**템플릿.** `${CLAUDE_SKILL_DIR}/templates/`에서 템플릿을 Read 도구로 읽어 `{{placeholder}}`를 치환합니다. 경로에 `${CLAUDE_SKILL_DIR}`가 치환되지 않은 채 보이면 이 SKILL.md와 같은 폴더의 `templates/`를 찾습니다.

- `CLAUDE.md.template` → CLAUDE.md
- `JOURNAL.md.template` → JOURNAL.md
- `ERROR.md.template` → ERROR.md
- `ISSUE.md.template` → ISSUE.md
- `WIKI.md.template` → WIKI.md

**치환 값 정리.** 사용자가 답한 값에만 적용하고, `{{CUSTOM_RULES}}`와 `{{DATE}}`처럼 정해진 값에는 적용하지 않습니다.
- 각 줄 맨 앞의 `#`과 그 뒤 공백만 지웁니다. 줄 중간의 `#`은 그대로 둡니다("C# 공부"는 바뀌지 않습니다).
- `<`로 시작해 `>`로 끝나는 태그를 지웁니다.
- 줄바꿈은 공백 하나로 바꿉니다.
- 200자를 넘으면 200자에서 자릅니다.

치환 변수:
- `{{PROJECT_NAME}}` → 인터뷰 1번 답변 (업데이트·업그레이드는 CLAUDE.md 첫 `#` 제목)
- `{{PROJECT_DESCRIPTION}}` → 인터뷰 2번 답변 (1-2문장 설명)
- `{{PURPOSE}}` → 인터뷰 2번 답변에서 핵심 목적만 추출 (한 구절)
- `{{AUDIENCE}}` → 인터뷰 3번 답변
- `{{TECH_STACK}}` → 인터뷰 4번 답변 (없으면 "해당 없음")
- `{{LANGUAGE}}` → 인터뷰 5번 답변 (기본: 한국어)
- `{{CUSTOM_RULES}}` → `<!-- 프로젝트 진행하며 자동으로 채워집니다 -->`
- `{{DATE}}` → 오늘 날짜 (YYYY-MM-DD)

### 7. GitHub 연결 (선택)

WHY: 클라우드 백업은 유용하지만, 공개 저장소로 만들면 작업 폴더가 인터넷에 공개된다.

아래가 **모두** 맞을 때만 제안합니다.
- 6-7 커밋이 성공했습니다.
- 하네스 루트에서 `git rev-parse --show-prefix`의 출력이 빈 줄입니다(하네스 루트가 저장소 최상위). 비어 있지 않으면 "이 폴더는 더 큰 저장소의 일부라서 GitHub에 올리면 그 저장소 전체가 올라갑니다"라고 설명하고 건너뜁니다.
- `gh auth status`가 성공합니다(gh가 설치되어 있고 로그인됨).
- `git remote get-url origin`이 **실패**합니다. 즉 원격 저장소가 아직 **없을 때만** 제안합니다. 이미 원격이 있으면 제안하지 않습니다.

질문은 선택지 질문 도구로 합니다. 저장소 이름은 영문 소문자와 하이픈으로 정해(한글 이름은 그대로 쓰지 않음) 질문 문장에 넣고("GitHub에 'my-blog' 비공개 저장소로 백업할까요?"), 비공개로 연결 / 나중에 가운데 고르게 합니다. 이름을 바꾸고 싶으면 기타(Other)로 받습니다. "비공개로 연결"을 골랐을 때만 실행합니다.

```
gh repo create <이름> --private --source="<하네스 루트>" --remote=origin --push
```

`--public`은 사용자가 공개를 따로 요청할 때만 씁니다. `gh`가 없거나 로그인되어 있지 않거나, Cowork처럼 push가 막히는 환경이면 "GitHub 백업은 나중에 내 컴퓨터의 터미널이나 Claude Code에서 언제든 할 수 있어요"라고 안내하고 건너뜁니다. 명령이 `Cowork blocked this request`로 막혀도 실패로 다루지 않고 같은 안내를 합니다.

완료 안내: "/ci 로 첫 체크인하세요."
